# 静态渲染与动态渲染

在 Next.js（以及现代 Web 开发）中，页面的 HTML 内容可以在不同的时间点生成，这产生了两种主要的渲染策略：**静态渲染**和**动态渲染**。

---

## 渲染时机的重要性

渲染时机直接影响：
- **首屏加载速度**（FCP - First Contentful Paint）
- **服务器资源消耗**
- **内容新鲜度**
- **用户体验**

选择正确的渲染策略是优化 Web 应用的关键决策。

---

## 静态渲染（Static Rendering）

### 原理

静态渲染是指在**构建（build）阶段**就预先渲染好页面内容，生成静态 HTML 文件。用户访问页面时，服务器直接返回这些预先生成的 HTML，无需实时计算。

```
构建阶段（开发/部署时）：
┌─────────────────────────────────┐
│  数据源 → 渲染引擎 → HTML 文件   │
└─────────────────────────────────┘

用户访问时：
┌─────────────────────────────────┐
│  CDN/服务器 → 返回 HTML 文件     │
└─────────────────────────────────┘
```

### 典型实现

- **SSG（Static Site Generation）**：Next.js 的 `getStaticProps`、`getStaticPaths`
- **ISR（Incremental Static Regeneration）**：增量静态再生成，定期重新生成特定页面
- 构建时生成，内容固定不变

### 渲染时机对比

```
时间轴 ──────────────────────────────────────────────────────→

静态渲染：
├─ 构建 ─┤                          ├─ 用户访问 ─┤
        └─ 生成静态 HTML ─┘                  └─ 立即返回 ─┘

动态渲染：
                                          ├─ 用户访问 ─┤
                                          └─ 实时渲染 ─┘
        └─ 每次请求都要计算 ─┘
```

### 优点

- **首次加载极快**：直接返回 HTML，无需服务器计算
- **TTFB（Time to First Byte）极低**：CDN 边缘节点直接响应
- **SEO 友好**：HTML 包含完整内容，爬虫容易抓取
- **服务器压力小**：可部署在 CDN 上，边缘节点直接响应
- **用户体验好**：首屏展示快，尤其适合网络条件差的场景
- **抗压能力强**：用户激增时不受影响，静态文件可被无限缓存

### 缺点

- **内容更新滞后**：需重新构建并部署才能更新内容
- **构建时间随页面数量增加**：大量页面会显著延长构建过程
- **不适用个性化内容**：无法根据用户身份动态生成不同内容
- **数据实时性为零**：用户看到的是构建时的数据

### 适用场景

- 博客、文档站（如 Next.js 官方文档）
- 产品介绍页、营销落地页
- 内容不频繁变化的网站
- 需要全球分发的应用（CDN 加速）

---

## 动态渲染（Dynamic Rendering）

### 原理

动态渲染是指**每次用户请求页面时**，服务器实时生成 HTML 内容。页面内容可以根据请求参数、用户身份、时间等动态变化。

```
用户访问时：
┌─────────────────────────────────┐
│  请求 → 数据获取 → 渲染 → 返回   │
└─────────────────────────────────┘
```

### 典型实现

- **SSR（Server-Side Rendering）**：Next.js 的 `getServerSideProps`
- **CSR（Client-Side Rendering）**：客户端渲染（如 React 默认方式）
- 请求时渲染，每次都重新生成

### TTFB 对比

```
时间轴 ──────────────────────────────────────────────────────→

静态渲染：
        ████ (几乎无等待)

动态渲染：
        ████████████████████████████ (需要等待服务端渲染)
```

### 优点

- **内容实时**：可展示最新数据，适合频繁变化的场景
- **个性化体验**：可根据用户角色、权限等定制内容
- **适合复杂业务**：如仪表盘、用户中心等
- **无需预构建**：页面即时生成，不受构建时间影响

### 缺点

- **服务器压力大**：每个请求都需要服务端计算
- **首次加载较慢**：比静态渲染 TTFB 更长
- **速度取决于最慢的数据取用**：页面必须等待所有数据都返回后才能渲染，如果某个数据源响应慢，整个页面就被 block 住
- **缓存复杂**：难以像静态资源那样简单部署在 CDN
- **部署更复杂**：需要 Node.js 服务环境
- **抗压能力弱**：用户激增时服务器压力成倍增加

### 性能特点

在动态渲染中，整个页面的渲染流程是：

```
用户请求 → 服务器开始渲染 → 获取所有数据 → 组装HTML → 发送页面
```

**关键点**：页面必须在**所有数据都拿到之后**才能发送给用户。如果任何一个数据请求很慢，整个页面就会被 block 住，直到最慢的那个请求完成。

### 数据请求阻塞问题

假设页面需要从 3 个来源获取数据：

```
数据源 A：50ms  ✓
数据源 B：800ms ✓ （最慢）
数据源 C：100ms ✓
```

**串行获取时**（常见于传统 SSR）：
```
开始 ──┬── A(50ms) ──┬── B(800ms) ──┬── C(100ms) ──┬── 完成
      │            │             │              │
      └────────────┴─────────────┴──────────────┘
      │←─────────────── 950ms ──────────────────→│
                    用户等待时间
```

**并行获取时**（现代 SSR 优化）：
```
开始 ──┬── A(50ms) ──┐
      │── B(800ms) ──┼── 完成
      │── C(100ms) ──┘
      │
      │←──── 800ms ──→│
       最慢的那个决定
```

无论并行还是串行，**最终响应时间 = 最慢数据源的耗时**。

### 适用场景

- 需要实时数据的页面（如股价、库存、实时排名）
- 个性化内容页面（如用户后台、订单列表、个人设置）
- 频繁更新的内容页面（如新闻、社交动态）
- 需要权限控制的页面（如管理后台）

---

## 对比总结

| 特性           | 静态渲染           | 动态渲染               |
|----------------|--------------------|------------------------|
| **生成时机**   | 构建阶段           | 每次请求时             |
| **TTFB**       | 极低（CDN 直接返回）| 较高（需服务端处理）    |
| **数据实时性** | 低（构建时）       | 高（请求时获取）       |
| **SEO**        | 非常友好           | 友好                   |
| **服务器压力** | 极小               | 较大                   |
| **缓存**       | 易于 CDN 缓存      | 缓存复杂               |
| **个性化**     | 不支持             | 支持                   |
| **构建时间**   | 随页面数增加       | 无需构建               |
| **抗压能力**   | 强                 | 弱                     |
| **适用场景**   | 内容少变页面       | 实时/个性化页面        |

## Next.js 中的渲染策略

### App Router 的默认行为

Next.js 的 App Router 默认采用**静态渲染**（Server Components 默认静态渲染）。

### 自动切换到动态渲染的条件

当页面中使用以下特性时，会自动切换为**动态渲染**：

- 使用 `cookies()`、`headers()`、`searchParams` 等请求相关 API
- 使用 `POST`、`PUT`、`DELETE` 等非 GET 方法
- 使用动态路由路径参数且未配置预渲染
- 使用 `no-store` 或 `revalidate` 配置的数据获取

### 手动控制渲染策略

可以通过 Next.js 的配置显式控制渲染策略：

```tsx
// 强制动态渲染
export const dynamic = 'force-dynamic';

// 强制静态渲染
export const dynamic = 'force-static';

// 仅缓存一段时间
export const revalidate = 60; // 60 秒后重新验证
```

### 渲染策略选择流程图

```
页面需要什么数据？
    │
    ├── 个性化数据（用户相关）───→ 动态渲染
    │
    ├── 实时数据（频繁变化）───→ 动态渲染 或 ISR
    │
    └── 静态/少变数据 ──────────→ 静态渲染
              │
              └── 内容极多？───→ ISR（增量静态再生成）
```

## 相关概念：流媒体（Streaming）

流媒体是解决动态渲染性能问题的关键技术，与静态/动态渲染是**互补关系**：

- **静态/动态渲染**：决定**何时**生成内容
- **流媒体**：决定**如何逐步交付**内容

详见笔记《流媒体 Streaming》

---

## 最佳实践

1. **优先考虑静态渲染**：能静态就静态，性能最优
2. **动态渲染时使用流媒体**：防止慢数据 block 整个页面
3. **使用 ISR 平衡新鲜度和性能**：定期重新验证，而非每次请求都重新渲染
4. **将数据获取下移到组件级别**：配合 Suspense 实现细粒度流式加载
5. **避免串行数据获取**：尽可能并行获取多个数据源
