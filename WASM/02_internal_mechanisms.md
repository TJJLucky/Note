第 2 章 — 内部机制与实现细节

1. 栈机与指令
- Wasm 使用基于栈的虚拟机模型（operand stack），每条指令从栈取值并把结果压回栈。相比寄存器式中间表示，栈机便于解析和形式化验证。

2. 验证器（Validator）
- 在加载阶段，Wasm 运行时会对模块进行静态验证：类型一致性、控制流结构合法、栈高度在每分支中可预测等。验证器是保证安全性的重要部分，防止类型混乱或未定义行为。

3. JIT 与 AOT
- 浏览器通常对 Wasm 做 JIT（即时编译）: 把 Wasm 翻译为本机指令；运行时还能做多级优化（baseline -> optimizing）。
- AOT（提前编译）用于边缘或原生嵌入式场景（如`wasmtime`/`wasmer`的 AOT 功能），可减少冷启动延迟。

4. 内存与地址空间
- 线性内存映射为 `ArrayBuffer`，可以与宿主共享或通过导出/导入完成零拷贝数据交换。
- 内存增长是通过 `memory.grow` 实现，内存大小按 page 增长。内存访问开销接近原生，但需要注意对齐和类型转换成本。

5. 调用约定与边界成本
- 跨界调用（Wasm ↔ 宿主）有固定开销：参数打包、类型转换、必要的边界与安全检查。减少小而频繁的跨界调用可显著提升性能。

6. 并发与线程
- Wasm 支持原子操作和 `SharedArrayBuffer`，允许在支持的宿主（启用跨源隔离）上实现多线程。但并发模型受宿主安全策略与平台支持限制。

7. 扩展与提案（演进方向）
- WASI（WebAssembly System Interface）：为 Wasm 提供可移植的系统调用抽象。
- GC Proposal：为高级语言提供本地垃圾回收支持，减少运行时桥接成本。
- Interface Types / Component Model：简化多语言互操作，封装复杂类型的序列化/反序列化。

8. 安全与沙箱
- Wasm 模块在沙箱内执行，不能直接访问宿主的任意资源。所有外部交互都通过显式导入函数或能力（capability）进行。

9. 调试支持
- 生成 `.wat`、保留 debug 符号或在 DevTools 中查看 Wasm 调用栈；`wasmtime`/`wasmer` 提供命令行运行与调试选项。

10. 小结
- Wasm 的实现关注验证、可编译性（JIT/AOT）、内存模型以及清晰的宿主边界。理解这些细节对编写高性能、可移植的 Wasm 代码至关重要。
